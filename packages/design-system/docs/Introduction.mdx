# Lar's design system

`@lar-works/design-system` holds Lar's tokens and theme, base styles, foundations and **generic components and
patterns**, and the rules that keep apps consistent (these docs and the lint rules in `@lar-works/config`). It names no
product: each app's own compositions, such as a board's rows, a media library's cards or a marketing page's device
frames, live in that app's UI layer (`src/ui`), built from what this package exports.

It is built on ninna-ui and Tailwind 4 for behaviour and utilities, with
[lucide](https://lucide.dev/icons) for icons. Apps never reach for those directly: they compose the components this
package exports.

## Installing it in an app

1. Add the package:

    ```sh
    pnpm add @lar-works/design-system
    ```

2. Import its styles once, at the top of the app's CSS. This brings in Tailwind, ninna-ui's preset, Lar's tokens and
   base styles, and the utilities the components use:

    ```css
    @import '@lar-works/design-system/styles.css';
    ```

    An app with a UI layer of its own imports `styles.css` with `source(none)`, then its layer's sheets, and has
    Tailwind scan only that layer:

    ```css
    @import '@lar-works/design-system/styles.css' source(none);
    @import './ui/board/board.css';

    @source './ui';
    ```

3. Wrap the app in `DesignSystemProvider`. It sets the icons' stroke width and supplies the design system's own words
   (Close, Cancel, Appearance…), which an app translates through its `labels` prop:

    ```tsx
    import { DesignSystemProvider } from '@lar-works/design-system';

    createRoot(document.getElementById('root')!).render(
        <DesignSystemProvider labels={{ theme: { label: 'Aparência' } }}>
            <App />
        </DesignSystemProvider>,
    );
    ```

Components come from `@lar-works/design-system`, icons from `@lar-works/design-system/icons`, and test helpers from
`@lar-works/design-system/testing`. An app's UI layer also takes `@lar-works/design-system/primitives`: the styleable
bases behind the components (`ButtonBase`, `BadgeBase`, `TextBase`, `StackBase`…, which take a class for the
composition's layout) and the hooks and recipes they share (`useScrollFade`, `linkRecipe`, `SplashView`…).

## Feature code never styles

An app has two kinds of code. Its **UI layer** (`src/ui`) holds the app's own compositions: it may lay them out and
style them with the design system's tokens and semantic utilities (`bg-surface-raised`, `text-fg-muted`, `gap-3`) and
its primitives, but never with a raw colour (`lar/no-raw-colours`), and it imports nothing of the app but other ui
files and shared types: labels, values and callbacks arrive as props. **Feature code** (everything else in `src`)
only composes components, the design system's and the UI layer's, and chooses their **semantic** recipes, such as
`<Button variant="destructive">` or `<Text variant="caption" tone="muted">`.

The lint rule **`lar/no-visual-recipes`** enforces this in an app's `src` outside `src/ui`. It reports:

- a `className` or `style` prop on any element;
- raw `h1`–`h6`, `p`, `button`, `input`, `select`, `textarea` and `svg` elements: use `Heading`, `Text`, `Button`,
  `IconButton`, `Input`, `Select`, `Textarea` and the icons instead;
- look props on design-system components, such as `size`, `color`, `weight`, `gap`, `radius` or `fullWidth`, and
  `variant` on form controls.

A companion rule, `lar/boundaries`, keeps `@ninna-ui/*`, `lucide-react`, Radix and Floating UI out of apps, so they
reach them only through this package's public API, keeps `@lar-works/design-system/primitives` inside `src/ui`, and
keeps app state, routing, services and features out of `src/ui`.

## When something is missing

If a screen needs a look that no component offers, compose it in the app's UI layer from the components, primitives
and tokens; extend a generic component here when the need is generic (a variant, a slot). **Promote** a composition
into this package when a second product needs it: give it a generic name and props, cover its states (loading, empty,
error, disabled, long text) and add a colocated `<Component>.stories.tsx`.

### Prop conventions

Components name their options the same way, so an app reads them alike:

- **`variant`** is a component's look among equals: `<Button variant="secondary">`, `<Text variant="caption">`.
- **`tone`** is a status colour, from one vocabulary: `neutral`, `info`, `success`, `warning`, `danger` (plus `accent`
  where a highlight is not a status). It never means a look of its own (`raised` is a `variant`), and a failure is
  `danger`, never `error`. Only the text components (Text, Heading, Link) add the colours of words: `default`,
  `muted`, `lead`, `soft` and a link's `inherit`. A confirmation's kind is ConfirmDialog's `intent`
  (`destructive` or `default`), not a tone.
- **`size`** is an object's scale on one ladder, `'xs' | 'sm' | 'md' | 'lg' | 'xl'`, of which each component takes
  the steps it has (StatusIndicator, Badge, BrandMark, ButtonLink). A single control or row that comes tighter is
  `size="sm"` (Button, Alert, StatusRow, ProgressStatusRow, Avatar, CollectionViewToggle, ScrollRow), never a boolean
  such as `compact`; a part's own scale is `…Size` on the same ladder. EmptyState and PageError name where they sit instead
  (`'hero' | 'start' | 'page' | 'panel' | 'compact' | 'inline'`). **`density`** is how tightly rows in a list or table pack
  (`'default' | 'compact'`).
- **`presentation`** is only for a structurally different layout of the same content (such as a card's `overview` and
  `row`), never a colour or a size.
- **Labels are props** (`label`, `backLabel`, `moreLabel`, …): components hold no copy, routing or i18n.
- **No `className`** on public props: an app cannot style a component, and the public types of components such as
  Button, Badge and Alert leave it out. Compositions, the design system's own and an app's UI layer, use the `…Base`
  export of such a component (`ButtonBase`, `BadgeBase`), from `@lar-works/design-system/primitives`.

### Empty, not-found and failed states

One grammar everywhere: an icon, what is (not) here, why, and the way forward.

- **EmptyState**: a region with nothing in it yet, or no results (`size` hero · start · page · panel · compact · inline).
  `compact` is centred and frameless with a small tile, for an empty list inside a settings panel or a popover.
- **PageError**: a page or region that could not be shown. Its `tone` says which of three different things happened:
    - **absence**, `neutral`: there is nothing here, such as a 404 (a `code="404"` is always neutral, whatever `tone`
      says) or no access. Say what isn't here and offer the way home, never a warning;
    - **temporary unavailability**, `warning`: it exists but can't be reached right now, such as a library whose
      folder is offline or a server restarting. Say when or why it comes back and what the reader can do meanwhile;
    - **load failure**, `danger`: reading it failed. Say what failed and offer **Try again**; technical details go in
      its `footer`.
- **AsyncState** owns a region's loading geometry and an inline load failure inside a form or dialog; **Alert** reports
  an operation's result or a condition of the surface. Write the notice **message first**: most Alerts are one
  sentence, `<Alert tone="warning" message="Metadata refresh is retrying." />`, in the regular weight. Add a `title`
  only when a few bold status words help scanning before the sentence (`title="Read-only folder"` with the sentence in
  `message`); a `title` alone still reads as the regular-weight message, for older callers, and `description` or
  children are the same slot as `message`. Its size follows the surface: inside a Modal, Drawer, pane, form or panel an
  Alert is `size="sm"` (the surfaces set it), so one notice (such as a shared-metadata notice) looks the same in every
  pane it appears in; `size="md"` is for a page-level alert only. **One recipe per tone, for every notice:** the
  tone's quiet surface, its hairline and its icon, with the words in the primary text colour. Never a grey box with a
  coloured edge, a plain bordered box, or a box without the tone's icon; ConfirmDialog's "what stays safe" note is an
  `info` Alert. Notifications (toasts) are popups: the neutral glass with the tone's icon and edge.

### Status words

One rule, the **status-word rule**: a **state**, what condition something is in (Merged, Failed, Running, Unavailable,
On, Problem, Waiting on #12), is a **StatusIndicator**: the state's coloured light, then its word in neutral text
(`<StatusIndicator state="failed" label="Failed" />`; ProgressStatusRow and an app's own state words follow it). Pick the `state` (ready, active, waiting, failed, off), never the colour. A **tone Badge** is only
for a **verdict or a category**, a judgement or a kind that isn't a condition: "Worth fixing", "Serious", "Probably this
one", "Check carefully", "Beta". A state is never a tinted pill, and never a word in a tone's text colour beside its
dot: the dot already carries the tone, and a row of coloured words reads as a row of alarms. A toolbar icon with
nothing to report is ToolbarStatusItem's quiet state (no `state` or `tone`), in the same box as a lit one.
`statusWordViolations` in `@lar-works/design-system/testing` finds tinted state words in an app's sources, beside
`problemBodyViolations`.

### Destructive actions

One rule, the **quiet-destructive rule**: a control that starts a destructive action (Delete, Abandon, Remove,
Revoke) is named in the danger text colour at rest, in a quiet weight, and gains the danger surface on hover or
keyboard focus. That is `<Button variant="destructive-quiet">` for an inline or footer trigger, `IconButton
tone="danger"` for an icon-only one and `DropdownMenu.Item destructive` in a menu. It opens a ConfirmDialog
(`intent="destructive"`), whose confirm button is the only solid red control (`variant="destructive"`). A destructive
trigger is never neutral grey text: it must not read as a harmless action.

### Leaving a dialog with unsaved changes

A Modal with `dirty` asks "Discard changes?" before Escape, a click outside, the close button or `Modal.Cancel` closes
it. A control inside it that leaves for somewhere else (another item's dialog, a link) calls `useModalClose()`'s
`requestClose(next)`: the same question, then `next` on Discard. Never a second discard dialog of the app's own.
That question, like every confirmation (`presentation="confirm"`, ConfirmDialog), has no close button and opens with
the focus on its safe answer (Keep editing, Cancel); Escape gives that answer too.

### Menus

A menu's entries are actions. When what it acts on is in a state worth knowing first (a library that is scanning), that
state heads the menu as `DropdownMenu.Status` (light, word, optional detail), never a disabled entry standing in for
it. Menus and popovers keep the app's 16px gutter from the window's edges and are nearly opaque, so artwork behind them
never reads through their rows.

## Finding your way around

- **Foundations**: the semantic tokens and the vocabulary rule, the scales (type, spacing,
  breakpoints, radii, elevation, motion), links, focus, the layering rule and entry points, and icons.
- **Typography**, **Actions**, **Forms**, **Display**, **Feedback**, **Navigation**, **Overlays**, **Collections** and
  **Layout**: the components, grouped as they are in `src/`.

Use the toolbar's theme switch to check every story in light and dark.
